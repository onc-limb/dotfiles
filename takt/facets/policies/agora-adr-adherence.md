# ADR 遵守ポリシー

設計のステップが `docs/adr/` に残した ADR を、実装とレビューが守るべき設計として扱う。

## 原則

| 原則 | 基準 |
|------|------|
| ADR を守るべき設計とする | 渡された設計レポートの ADR 一覧にある ADR を、`docs/adr/` の本文で読んでから作業する。要約だけで判断しない |
| 前提を確かめる | ADR の「前提」が現在のコードや要求と合っているかを見る。合わないと分かったら、その事実を報告する |
| 決まっていない設計判断を自分で決めない | ADR に書かれていない設計判断が必要なら、実装でもレビューの修正案でも決めない。必要な判断を報告して止まる |
| 置き換えられた ADR に従わない | ステータスが「置き換え」の ADR は守る対象にしない。置き換えた新しい ADR に従う |

## 設計から外れた実装と、足りない設計判断

この 2 つは別のものとして扱う。

| 状況 | 扱い |
|------|------|
| ADR に書かれた結論、採用の理由、影響範囲に反する実装 | 設計から外れた実装。通常の指摘として直す |
| ADR のどれにも当たらず、実装を選ぶ前に決める必要がある設計判断 | 足りない設計判断。直さずに報告する |

足りない設計判断を報告するときは、「ADR に書かれていない設計判断」という見出しで、決める必要がある内容、候補になりそうな選択肢、それが実装のどこに影響するかを書く。

## 判定基準

| 基準 | 判定 |
|------|------|
| ADR に反する実装を、設計から外れたものとして指摘していない | REJECT |
| ADR を読まずに ADR に沿っていると報告している | REJECT |
| 足りない設計判断を、実装やレビューの修正案で決めている | REJECT |
| 足りない設計判断を、設計から外れた実装の修正として扱っている | REJECT |
| ADR の結論を変える修正を、実装側の判断で行っている | REJECT |
| ADR に沿っていることを、読んだ ADR の番号とコードの該当箇所で示している | OK |
