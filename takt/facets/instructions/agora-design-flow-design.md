# 設計して ADR に残す

タスクの文面から、実現方法を比べて設計を決め、設計判断を `docs/adr/` に ADR として残してください。コードの実装はしないでください。

## 読むもの

1. タスクの文面
2. `agora-design` ポリシー
3. これまでの ADR。`agora adr list` で一覧を出し、今回に関わるものは `agora adr show <番号>` で本文を読む。`docs/adr/` が無い、または ADR が 0 件でもそのまま進める
4. 設計の知識。`agora knowledge show --scene design` で出し、必要なら `--granularity` と `--lang` で絞る
5. 影響範囲を調べるための現在のコード

Report Directory に前回の設計レポートや検証レポートがある場合は、再設計として扱う。検証レポートの「ADR に書かれていない設計判断」に書かれた判断が足りない設計である。その判断を決め、ADR を足すか直す。

## 設計

- 実現方法を 2 案以上挙げ、比べる。1 案しか思いつかない場合も、採らない案（何もしない、既存の仕組みを使う、など）を挙げる
- 推奨案を 1 つ選ぶ。人に聞かずに任せる進め方なので、推奨案をそのまま採用する
- 影響範囲を特定する。変わるファイル、変わるモジュール、外から見える振る舞いを分けて書く
- 設計判断が 1 つも要らないタスク（既存の ADR と知識だけで決まる）なら、ADR を作らない。その理由を、どの ADR・知識に従うかとともにレポートへ書く

## ADR を作る

設計判断 1 つにつき ADR を 1 件作る。1 件に複数の判断を混ぜない。

1. `agora adr new "<題名>"` で雛形から作る。ステータスは「提案」で作られる
2. 雛形の節（結論・背景・前提・検討した案・採用の理由・影響範囲）をすべて埋める。空の節や雛形の説明文を残さない
3. 「検討した案」に、採用しなかった案と採用しなかった理由を書く
4. 「前提」に、この判断が成り立つ条件を書く。前提が変わったら見直せるようにするため
5. ステータスを「提案」から「採用」に書き換える

再設計で前の判断を置き換えるときは、古い ADR のステータスを「置き換え」にし、新しい ADR の本文から古い ADR の番号を参照する。前の判断を直すだけで済む場合は、その ADR を直接直し、レポートに直した箇所を書く。

## 実装の担当への引き渡し

設計レポートに、実装の担当とレビュー役が読む ADR の一覧（番号・題・ステータス・パス）と、守るべきルールの要点を書く。出力形式の「実装の担当とレビュー役が従う取り決め」は、実装とレビューの担当がレポートから読む唯一の取り決めなので、必ず書く。ADR を作らなかった場合も、従う既存の ADR と知識を書く。`agora knowledge show --scene delegate` に渡し方の知識があれば使う。

次の status を 1 つだけ選択してください。
- `designed`: 設計を決め、ADR を作った、または作らない理由をレポートに書いた。
