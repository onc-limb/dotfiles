**この回は、レビューの裁定を経ていません。**

最初のレビューで、動かしたレビュアーの全員が承認しました。直す対象を決める裁定の工程は、指摘が無いので省いています。そのため、上の「現在のレビュー裁定」は、この run に無いと表示されるか、今回のレビューより前の回のものです。上の指示のうち、裁定のレポートを前提にした部分は、次のように読み替えてください。

- 裁定のレポートが無いことを、REJECT や BLOCKED の理由にしない
- 前の回の裁定が出ている場合、そこに書かれた問題は「解消済み」として扱わない。現在のコードを読んで、解消しているかを自分で確かめる
- 要件の充足は、指示書と計画の要件を 1 つずつ、現在のコードに照らして確かめる。レビュアーが承認したことを、充足の根拠にしない

裁定の工程が見るはずだった次の 2 つも、ここで確かめてください。

- Report Directory の各レビューレポートにある「指摘にしなかった懸念」（testing-review では「未確認範囲」）
- 計画レポートの「留意点」（通常の計画では「確認事項（あれば）」）

どちらも、指示書・計画・プロジェクトの決まりに根拠があり、現在のコードで満たされていないものだけを、未充足として扱ってください。根拠の無いものは、持ち越しとして summary.md に書くだけにします。

REJECT にした場合、この後に裁定の工程が動き、あなたのレポートを読んで直す対象を確定します。未充足の要件ごとに、破られている条件、根拠（指示書・計画の該当箇所と file:line）、受入条件、最小の修正境界を、裁定がそのまま使える形で書いてください。
