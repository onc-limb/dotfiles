# 設計への適合を検証する

実装が、設計のステップが残した ADR と `agora-design` ポリシーの「確かめること」に沿っているかを検証してください。実装の経緯を知らない状態で、ADR・ポリシー・現在のコードだけを根拠にします。ファイルを編集しないでください。

## 読むもの

1. Report Directory の設計レポートにある ADR 一覧と、その本文（`docs/adr/` の該当ファイル）。ステータスが「置き換え」の ADR は守る対象に含めない
2. `agora-design` ポリシーの「確かめること」
3. 実装の差分と、変更されたファイル
4. 前段の実装・レビューのレポート（Report Directory にあるもの）

## 検証

- ADR ごとに、結論・採用の理由・影響範囲がコードに反映されているかを、コードの該当箇所で確かめる
- ADR の「前提」が、現在のコードと要求に対して成り立っているかを確かめる
- `agora-design` の「確かめること」の各項目を、変更されたコードに当てて確かめる
- ADR を作らないと設計レポートに書かれていた場合は、その理由が成り立つか（従うと書かれた ADR と知識に実装が沿っているか）を確かめる

## 結果の振り分け

次の 3 つは別のものとして扱う。取り違えない。

| 状況 | 選ぶ status |
|------|------------|
| ADR はあるのに、コードがそれに反している、または `agora-design` の項目に反している | `deviation` |
| ADR のどれにも当たらず、実装を選ぶ前に決める必要がある設計判断が実装中に出た | `undecided` |
| 反映も判断の不足もなく、すべて沿っている | `conforms` |

- `deviation` は、ADR の結論を変えずにコードを直せば解消する。反している箇所と、ADR のどの記述に反するかを書く
- `undecided` は、ADR を直さない限り実装側では決められない。足りない設計判断（決める内容・選択肢・影響する箇所）を、検証レポートの「ADR に書かれていない設計判断」へ書く。コードで直せる箇所を `undecided` にしない
- ADR を守ると別の不具合が出る場合や、ADR の前提が成り立たなくなっている場合は、ADR の判断を変える必要があるので `undecided` とする
- 前段の実装が最後まで終わらずに止まった場合は、止まった理由が足りない設計判断なら `undecided`、それ以外（設計と関係のない失敗や外部の待ち）なら `blocked` とする。コードが ADR に沿っていることだけでは `conforms` にしない

次の status を 1 つだけ選択してください。
- `conforms`: すべての ADR と `agora-design` の項目に沿っている。
- `deviation`: ADR または `agora-design` の項目から外れた実装があり、修正で直せる。
- `undecided`: ADR に書かれていない設計判断が必要で、設計のステップでの再設計が要る。
- `blocked`: 設計とは関係のない理由で実装が完了しておらず、再設計でも直らない。
